# Session 6 — the whole pipeline runs on the phone, from an APK

**Date:** 2026-08-23
**Outcome:** prompt → 49-frame video, entirely on the S25 Ultra, from a standalone debug
APK with no network and no adb. **23.5–26.9 s** per video; **7.2 s** for a single image.

This is the first session where the port stopped being a collection of measured modules and
became a thing you can hold. Twelve context binaries (7.96 GB) sit in the app's external
files dir; the app loads them onto the HTP itself.

## The one that mattered: an app cannot exec its way onto the DSP

The desktop harness drives every graph by exec'ing `qnn-net-run` over adb, so the first
APK shipped that same binary inside the APK as `libqnnnetrun.so` (Android marks
`lib*.so` in `nativeLibraryDir` executable, which is the usual trick). It runs — it prints
its build banner and reads its inputs — and then dies in backend init:

```
QnnDsp <E> loadRemoteSymbols failed with err 4000
QnnDsp <E> Failed to load skel, error: 4000
Device Creation failure
```

That reads like a missing library or a wrong `ADSP_LIBRARY_PATH`. It is neither. Bisected
on device, the **byte-identical binary** (same md5), with identical `LD_LIBRARY_PATH`,
identical skel directory and identical working directory:

| exe location | SELinux context | DSP |
|---|---|---|
| `/data/local/tmp/nd/qnn-net-run` | `shell_data_file` | **works** |
| `<apk>/lib/arm64/libqnnnetrun.so` | `apk_data_file` | **fails** |

The only variable is where the executable lives. A process exec'd out of the APK is denied
the Hexagon fastrpc device, and no arrangement of the environment changes that. **The
backend must be `dlopen`'d into the app process**, which already holds the permission.

That is `work/android/app/src/main/cpp/ndqnn.cpp` — a ~600-line in-process runner over the
QNN API: `QnnInterface_getProviders` → `backendCreate` → `deviceCreate` →
`systemContextGetBinaryInfo` (for tensor names, shapes and encodings) →
`contextCreateFromBinary` → `graphRetrieve` → `graphExecute`.

Two things fell out of the rewrite for free:

* **Graphs stay resident.** The exec path re-read the context binary on every inference.
* **The input-format footgun disappears.** `--use_native_input_files` was required for
  integer inputs to float graphs and forbidden for quantised ones, and getting it wrong
  produced identical plausible output for every prompt (trap #8). In-process, the native
  side reads each tensor's real dtype and encoding out of the binary and converts
  accordingly. There is nothing left to get wrong.

### …and then the vendor library

With the backend in-process, `deviceCreate` still failed. Forwarding QNN's own log to
logcat (it is discarded by default) gave the real reason immediately:

```
Failed in loading stub: dlopen failed: library "libcdsprpc.so" not found:
    needed by libQnnHtpV79Stub.so in namespace clns-9
```

`libcdsprpc.so` is a **vendor** library. It is listed in `/vendor/etc/public.libraries.txt`
on this device, so it is linkable in principle — but from `targetSdk` 31 an app must also
declare it:

```xml
<uses-native-library android:name="libcdsprpc.so" android:required="true" />
```

Without that one line the failure surfaces four layers up as `Failed to load skel,
error: 4000`, which points nowhere near the cause.

## New traps

**33. An app cannot exec a helper binary onto the DSP.** Byte-identical binary, same libs,
same env, same CWD: works from `/data/local/tmp` (`shell_data_file`), fails from
`/data/app` (`apk_data_file`). Load the backend in-process instead. Bisect exec-location
problems by *moving the binary*, not by editing the environment.

**34. Declare `libcdsprpc.so` with `<uses-native-library>`.** Required from targetSdk 31
even for a library the platform lists as public. And **forward QNN's log callback to
logcat** — the diagnosis is in QNN's own output, which is thrown away by default.

**35. `mmap` context binaries; do not read them into the heap.** Reading a 1.4 GB binary
before handing it to `contextCreateFromBinary` doubles peak footprint for the duration of
the load. On an 11 GB phone that was enough to draw lmkd's attention: `MemFree` was
observed at **110 MB** with eight background apps culled in a single sweep, and the
Activity was killed mid-run. `mmap` + `MADV_SEQUENTIAL`, plus releasing each graph when the
pipeline is done with it, took peak RSS **1.57 GB → 0.40 GB** with no latency change.

**36. Precompute deterministic bookkeeping on the host; port only arithmetic.** The AR
loop's hard parts — the padding envelope, which history slices form the past conditions,
the temporal RoPE ids, the token layout — depend only on `(unit_index, stage)`, never on
the prompt, seed or any latent value. All 18 combinations were computed once against the
reference (`work/export/export_video_structure.py`, 4.2 MB asset) instead of reimplementing
`_prepare_past_condition_latents`, `align_to_envelope`, `_prepare_temporal_rope_ids` and
`temp_rope_embed` in Kotlin — four chances at a silent off-by-one whose output looks
plausible either way. The masks themselves are *not* shipped (214 MB); they are rebuilt on
device from `order` + `image_valid` + the text mask, which is the only prompt-dependent
part.

**37. The video path uses different text encoders from the first-frame path.**
`TextEncoderBundle` loads `text_encoder` / `text_encoder_2` (both
`CLIPTextModelWithProjection`) and keeps only their **pooled** `text_embeds`, concatenated
to the MMDiT's 2048-d `pooled_projections`. The shipping `clipl` graph was exported from
`ssd_1b_text_encoder`, a plain `CLIPTextModel` with **no projection head**, so it cannot
supply that vector — hence the new `cliplp` build. The two checkpoints are the same weights
at different precisions (bf16 vs fp16, max abs difference 0.027 across all 517 shared
tensors), so CLIP G's existing graph serves both paths.

**38. The streaming decoder packs frames FRAME-major.** `video` is `[1, 24, 320, 512]`, and
frame *f* owns channels `[3f, 3f+3)` (`export_vae_decoder_stream.py:171`). Reading it
channel-major yields three plausible greyscale videos. `frames_to_trim = 7` applies to the
whole video, not per invocation: 7 latent frames × 8 = 56 emitted, minus 7, is 49.

**39. Feed the decoder's state outputs straight back as its state inputs.** The 9 MemBlock
states are channel-last in the shipping build, which is why the desktop path needed
`permute_states_nhwc.py`. In-app, `nstate_i → state_i` without ever interpreting the
contents makes the layout question disappear entirely, and the sizes come from the binary's
own metadata rather than being hardcoded.

## Host-side assets in the APK (57 MB)

| asset | what |
|---|---|
| `ssd1b_addembed.ndw` | SSD1B `add_embedding`, 20 MB — the only weighted module the first-frame path keeps on the host |
| `mmdit_temb.ndw` | MMDiT `time_text_embed`, 31.5 MB |
| `video_structure.ndw` / `.json` | RoPE tables + token layout for all 18 calls, 4.2 MB |
| `clip_vocab.json` / `clip_merges.txt` | CLIP BPE, 1.5 MB (both SDXL tokenizers share one vocab) |
| `t5_unigram.tsv` | 32100 Unigram pieces + scores, 650 KB |
| `pipeline_config.json` | LCM schedule, sinusoid parameters, VAE factors, pad ids |

Every sinusoid is computed in Kotlin at fp32 and passed in as an ordinary tensor. That is
the same decision that bought the MMDiT 8.41 dB: quantising a `Sin` at its *argument*
(encoded over [0,1000] at 16 bits) caps you near 47 dB.

## Still open

* The MMDiT accuracy work is **done** — see `notes/2026-08-23-adaln-fix.md`, earlier the
  same day: both fixes built, giving 27.89 / 23.99 / 20.01 dB at 408 / 648 / 1728 tokens
  against targets of 29 / 22 / 24. Stage 1 MET; stage 2 is the worst gap (-3.99) because it
  has the longest sequence *and* the highest target.
* The MMDiT is **14.4 s of the ~23.5 s video** (6 x (169.2 + 375.8 + 1851) ms), a steady
  1.6-2.0x the paper. That, not context loading, is where the wall clock goes.
* `mmdit_s0r` (per-row stage 0) is converted but never measured.
* QuickSRNet is the only module never converted.
* Playback is a Compose frame-stepper, not an encoded file. Nothing writes an MP4 yet.
