## THE ONE THING TO DO NEXT

MMDiT stage 0 runs on device at **19.47 dB against a 29 dB target**. The cause is
**identified and confirmed from the converter's own graph**, not guessed:

```
_MatMul     q[UFIXED_16] x kT[UFIXED_8]  -> scores      # K is 8-bit
_MatMul_1   scores[UFIXED_16] x v[UFIXED_8]             # V is 8-bit
```

QNN treats a MatMul's **second operand as a "weight"**, and 16-bit *dynamic* weights are
off by default — so **K and V, which are pure activations, are quantised to 8 bits** in
every one of the 18 attention blocks. The converter says so explicitly during conversion:

> `mixedPrecisionForWeights: The override provided for the following weight:
> /Transpose_71_output_0 would not be honoured. Since 16 bit dynamic weights are not
> supported by default. Kindly use the flag --use_dynamic_16_bit weights`

### The fix to try

`--use_dynamic_16_bit_weights` is a **real but hidden flag** (`argparse.SUPPRESS` at
`qnn_quantizer.py:156`, default `False`, passed through unless backend is `lpai`).
The help text for `--restrict_quantization_steps` says it "is required for 16-bit Matmul
operations", and it is accepted because we pass `--use_per_channel_quantization`
(gate at `qnn_quantizer.py:399`). So add **both**, as one coherent change:

```
--use_dynamic_16_bit_weights
--restrict_quantization_steps "-0x8000 0x7F7F"
```

to the converter invocation in `work/qnn/convert_mmdit_w8a16.sh`.

**Check first (5 minutes, may save 40):** confirm HTP supports 16-bit MatMul operands
before committing to a full run — look for a MatMul datatype constraint in
`../LocalDream/qairt/2.49.0.260730/lib/python/qti/aisw/converters/common/backend_aware_configs/htp.json`.
MaskedSoftmax was already ruled out this way (see "Ruled out" below).

Then: full conversion (~40 min) → push → run → `compare_mmdit.py --stage 0`.

## The MMDiT accuracy diagnosis, in full

So the next session does not repeat any of it.

**Symptom.** 16 held-out cases: mean 19.47 dB, min 12.05 dB, target 29 dB. No NaN/inf.
Outputs distinct across cases (trap #8 clear). So the graph is *correct*, just imprecise.

**Ruled out — padding.** Per-case SNR correlates with padding fraction (r = −0.66) and the
three worst cases are all unit 1 (200 of 280 image tokens padded). But
`work/audit/mmdit_residual_scan.py` shows padded tokens peak *lower* than real ones —
**padded/real ratio 0.59×**. Padding is a second-order effect, not the cause.

**Ruled out — outlier-dominated activation ranges.** `analyze_encodings.py` found late
residual adds with range 55,130 and step 0.84 against a graph median range of 24.47, which
looked exactly like trap #3. But the residual scan shows **max/p99.99 is only 1.1–1.5×** on
the image stream: the distribution is genuinely wide, not outlier-driven. Percentile or MSE
activation calibration would reclaim almost nothing. **Do not spend a conversion on
`--act_quantizer_calibration percentile`.**

**Also measured:** the residual genuinely grows **197 → 27,922 (140×) across 18 blocks** on
the text stream, 1,699 → 17,808 on the image stream. Real, but computing per-tensor SQNR
from (range, std) gives **60–80 dB everywhere** — which cannot explain a 19 dB output. That
is what sent me looking at operand precision instead, and found the 8-bit K/V.

**Not yet tried, in priority order:**
1. `--use_dynamic_16_bit_weights` (+ `--restrict_quantization_steps`) — above
2. `--use_per_row_quantization` for the FullyConnected weights
3. `--algorithms cle` (cross-layer equalisation)
4. Residual scaling, trap #3's Phase 1 fix, folded into weights — the biggest change

## Latency: 248.3 ms vs the paper's 104.7 ms

Not yet investigated. Min-of-3-rounds in one thermal session (trap #10 respected).
Transposes are already clean (ratio 0.25, 92.04 MB ≈ 23 ms at the measured 0.252 ms/MB),
and there is **zero float fallback**, so neither is the explanation.

The obvious next step is a **per-op profile**: re-run with `--profiling_level detailed`
and use `work/device/analyze_prof.py` (written for Phase 1). Suspects worth checking in the
graph: `Reshape` ×778 and `StridedSlice` ×324 — a lot of nodes for 18 blocks. Note the
converter's own MAC counter reports 2.32 GMAC for this graph, which is ~266× too low
against a hand estimate of ~617 GMAC (1512 M params × 408 tokens) — **do not trust
`reEvalMacsParams` on this model.**

## Environment gotchas hit this session

- **Run `wsl` from PowerShell, never the Bash tool.** `wsl -d Ubuntu -e bash /mnt/c/...`
  through Bash became `C:/Program Files/Git/mnt/c/...` and **exited 0 having done nothing.**
  Same rule CLAUDE.md already had for adb.
- **Heredocs keep failing** for large files — use the Write tool.
- **Assert on every scripted edit.** Two patches failed their asserts instantly this session
  (wrong anchor, `--`/`—` mismatch) and cost nothing; the ones without asserts are the ones
  that silently do nothing.
- **Do not run a host-side Python job that needs ~7 GB while WSL holds 10 GB** — the machine
  has 15.6 GB total and both will thrash. One converter run degraded from 6:26 to 22+ min
  and had to be killed.
- `adb push` of the 1.5 GB binary failed once with exit 1 and succeeded on a plain retry.
  Always verify with `stat -c %s` (both push scripts already do).
