## THE ONE THING TO DO NEXT

**Get the layerwise dump. Everything else is eliminated.**

Six hypotheses are dead, and the last experiments changed the character of the problem:
**a faithful host simulation of this exact graph cannot reproduce the device.**

| what is quantised (host, fp32 torch, real net.json encodings) | SNR |
|---|---|
| residual block boundaries only | 53.33 dB |
| AdaLN / modulation chain, A16, 246 points | 52.07 dB |
| W8 per-channel weights only (1498 M params) | 43.14 dB |
| weights + all Linear outputs + softmax | 43.11 dB |
| **the device** | **19.48 dB** |

Sanity: the fp32 rerun driven by the device's own input raws matches the stored `nref`
at 130.03 dB, so inputs and reference are consistent. Calibration is tight (enc/act
median 1.21x, `enc_vs_actual.py`). Of 2374 nodes, **1127 preserve their input encoding
exactly and contribute zero error**; 1247 genuinely requantise, and the two largest
groups are ablated above.

So the device is doing something worse than a correct W8A16 execution of its own graph.
That is no longer a calibration or bit-width question -- it is a question about what the
hardware actually computes, and only intermediate values will answer it.

**Prime suspect, untestable from the host:** op-internal precision in the norms (144
requantisation points). Trap #3 established that HTP runs float graphs in fp16 with no
fp32 upcast in the layer norm; the text-stream residual reaches **52,000** by block 14,
and `mean(x^2)` on that needs 2.7e9 of headroom against fp16's 65504 ceiling. **Do not
assume this** -- five confident mechanisms have already died on this module. Measure it.

Host ablation tools, all reusable: `resid_ablate.py`, `quant_ablate.py`,
`adaln_ablate.py`, `enc_vs_actual.py`. Encoding convention, verified:
`real = scale * (q + offset)`, `q` in `[0, 2**bits - 1]`.

### The prerequisite, discovered the hard way

`work/device/find_block_io.py` and `work/device/block_snr.py` are **written, tested and
ready**. What is missing is the dump they consume, and getting it is blocked:

| approach | status |
|---|---|
| `qnn-net-run --set_output_tensors` on the phone | ❌ *"can only be used with graph prepared online using --model or --dlc_path"* |
| `qnn-net-run --debug` on the phone | ❌ same restriction, explicitly excludes `--retrieve_context` |
| host CPU backend + the x86 model lib we already have | ❌ `[QNN_CPU] OpConfig validation failed for Transpose` — the rank-5 latent transpose is unsupported |
| **aarch64-android model lib + `--debug` on device** | ✅ the way through — **needs the Android NDK, which is not installed** |

So the sequence is:

1. Install the Android NDK; set `ANDROID_NDK_ROOT`.
2. `qnn-model-lib-generator -c $OUT/mmdit_s0.cpp -b $OUT/mmdit_s0.bin -t aarch64-android`
   (`aarch64-android` is a supported target and is even one of the two defaults).
3. Push the resulting ~1.5 GB `.so`, run `qnn-net-run --model ... --debug` on **one**
   input (`mio_s0/one_input.txt`, already on device). Online graph prep for a 1.5 GB
   model will be slow — this is a one-off, not a per-run cost.
4. `py -3.10 work/device/find_block_io.py work/device/mmdit_s0_net.json --emit`
   → pull only those 35 raws (~45 MB of the ~4 GB dump).
5. `py -3.10 work/device/block_snr.py --stage 0 --names "$(cat work/device/blocknames_s0.txt)"`

**The shape of the answer prescribes the fix**, which is why this is worth the setup:
smooth per-block degradation ⇒ error accumulates down the residual chain ⇒ residual
scaling folded into weights (trap #3). A cliff at block N ⇒ one op. Bad after block 0
⇒ patchify/conditioning, not the blocks.

## What was measured this session

### Latency — solved

| | baseline | RoPE rewrite | Δ |
|---|---|---|---|
| latency (min-of-3) | 248.3 ms | **172.2 ms** | **−30.6%** |
| deploy SNR | 19.47 dB | 19.48 dB | unchanged (correct — the rewrite is exact) |
| `Concat` cycles | 108,710,352 (28.7%) | **103,527 (0.0%)** | **−1050×** |
| converter wall | 35:04 | 35:04 | unchanged |

**RoPE was 43.3% of the entire graph** — 6.6× all 255 FullyConnected layers combined.
28.7% was a single line, `torch.stack([out_even, out_odd], dim=-1)`, which lowers to an
**element-by-element interleave**. For contrast the 54 concats joining the text and
image streams on axis 0 — *twice the volume* — cost **exactly zero cycles**, because
QNN folds an outermost-axis concat into its producers. The cost was granularity, not
bytes, which is why no byte-counting tool could see it.

The fix contracts the rotated halves separately —
`⟨q',k'⟩ = ⟨q'_even,k'_even⟩ + ⟨q'_odd,k'_odd⟩` — so they never need reassembling.
Identical FLOPs. Verified at all 18 shapes at 123–127 dB (the fp32 floor).

### Accuracy — six hypotheses dead

1. **Padding** (prior session) — padded tokens peak *lower* than real, 0.59×.
2. **Outlier ranges** (prior session) — max/p99.99 only 1.1–1.5×.
3. **8-bit K/V** — the previous handoff's headline fix. The mechanism is **real** and
   the flags work exactly as advertised (`matmul_bits.py` confirms all 36 MatMuls move
   `u16 × u8` → `u16 × u16`, and the 255 FullyConnected keep static `u8`). Result:
   **+0.01 dB, +18.6% latency, +21% conversion time.** Now off by default; `DYN16=1`
   re-enables it.
4. **The −100 attention mask** inflating score encodings — killed **for free** by
   reading `net.json`: the mask widens the score range 1.68×, i.e. 0.75 effective bits.

5. **Residual accumulation** (trap #3's argument, the standing lead going in) —
   replaying the real `net.json` encodings on the 35 block boundaries gives **53.33 dB**.
   The residual chain is not the cause, so residual scaling is not the fix.
6. **W8 weights** — 8-bit per-channel on all 249 Linear (1498 M params) gives
   **43.14 dB**; adding Linear-output and softmax activation quantisation moves it to
   43.11 dB.

**And the finding that supersedes all of them:** nothing reproduces 19.48 dB. A faithful
host simulation of this graph — real encodings, correct convention, verified plumbing
(fp32 rerun vs `nref` = 130.03 dB) — bottoms out at ~43 dB. The device is ~23 dB worse
than a correct W8A16 execution of its own graph, so the cause is **not ordinary
quantisation**. See the top of this note and `docs/phase5-mmdit-accuracy.md`.

## Environment notes

- **WSL tore itself down twice mid-run**, killing background tasks (`systemd-journald`
  ELAPSED resets prove it — the VM restarted, the processes did not crash). Steps 1/3
  and 2/3 had already exited 0 both times, so `finish_ctx.sh` recovered it in 76 s.
  **Check `ps` in WSL before assuming a long job is still running.**
- **The 1.5 GB `cp` from ext4 to `/mnt/c` was interrupted** and left a 581 MB file that
  looked plausible. Always verify by size; `push_mmdit.ps1` already does.
- **Wireless adb fails the 1.5 GB push** more often than not (2 failures), but succeeded
  on a plain retry at 14.7 MB/s / 100 s. **USB did it in 45 s** — worth plugging in, and
  note the phone attaches on both transports at once (trap #14), with USB dropping
  in and out during this session.
- A safety hook blocks `rm -rf` inside `adb shell` command strings — use a fresh output
  directory instead.
