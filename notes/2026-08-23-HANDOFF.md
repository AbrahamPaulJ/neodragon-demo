## THE ANSWER: it is the AdaLN modulation path, not the image path

After seven dead hypotheses, the intermediate values settle it in one run. Inside
block 0, the two paths that meet at `norm1` have completely different quality:

| path | tensor | SNR |
|---|---|---|
| **image tokens** | `_Concat_output_0` (patchified, all 3 latents) | **54.05 dB** |
| **image tokens** | `_norm1_norm_LayerNormalization_output_0` | **54.96 dB** |
| conditioning | `_time_text_embed_time_proj_Sin_output_0` | 46.41 dB |
| conditioning | `_time_text_embed_timestep_embedder_act_Mul_output_0` | 28.50 dB |
| conditioning | `_norm1_silu_Sigmoid_output_0` | 24.71 dB |
| conditioning | `_norm1_linear_Gemm_output_0` `[1,9216]` | 29.35 dB |
| **modulation chunks** | `_norm1_Slice_{0..5}` | **13.90 – 34.85 dB** |
| **modulation chunks** | `_norm1_context_Slice_{0..5}` | **11.97 – 27.50 dB** |
| **they meet** | `_norm1_Mul_6_output_0` = `norm(x) * (1+scale)` | **21.18 dB** |
| **they meet** | `_norm1_Add_2_output_0` = `... + shift` | **16.51 dB** |

**A 55 dB image stream is destroyed by a 14 dB modulation vector.** Everything after
that — attention at 20–28 dB, `_to_out_0_Add_output_0` at 16.15, `_Mul_10_output_0` at
14.79, `_Add_9_output_0` at 12.54 — is downstream of it. Block 0 ends at 23.49 dB and
the graph never recovers.

### Two distinct, independently fixable causes

**1. The six AdaLN chunks share ONE encoding.** `norm1.linear` emits `[1, 9216]`,
which is `chunk(6)` into shift/scale/gate for MSA and MLP. The tensor's encoding is set
by its largest chunk (`max|ref|` 18.41), so the small ones — 1.682, 2.046, 2.503 —
spend 3–4 of their 16 bits on range they never use:

| chunk | `max|ref|` | SNR |
|---|---:|---:|
| whole Gemm output | 18.41 | 29.35 dB |
| `_norm1_Slice_3` (shift_mlp) | **1.682** | **13.90 dB** |
| `_norm1_Slice_0` | 2.046 | 16.93 dB |
| `_norm1_context_Slice_0` | 2.503 | 11.97 dB |
| `_norm1_Slice_5` (the one that sets the range) | 18.41 | 34.85 dB |

The predicted penalty from the magnitude ratio alone (20·log₁₀(18.41/1.682) = 20.8 dB)
lands on top of the observed spread. **This is a converter-visible structural fault, not
a calibration one**, and no amount of better calibration fixes it — the range is
genuinely needed by one of the six.

**Fix: split `norm1.linear` into six separate Linear ops** by slicing the weight and
bias rows, so each chunk gets its own encoding. Identical FLOPs, identical arithmetic,
36 more nodes. Same family as traps #1 / #11 / #16 / #23 / #26 — the win comes from
removing structure the backend cannot see through. `docs/phase5-mmdit-latency.md`
already flagged "fold the AdaLN `chunk(6)` slices" as a ~11% *latency* lever; it turns
out to be the *accuracy* lever too.

**2. `time_proj`'s sinusoid is quantised at its argument.** `timestep_ratio` carries the
encoding `[0, 1000]` at 16 bits — a step of **0.0153 rad**. `Sin` of an argument with
that step has a ceiling of about 20·log₁₀(1 / (0.0153/√12)) ≈ **47 dB**, and it measures
**46.41 dB**. The SiLU multiply then takes it to 28.50 dB before it ever reaches a block.

**Fix: hoist `time_text_embed` to the host.** `temb` depends only on `timestep_ratio`
and `pooled_projections`, both of which the host already computes, and its weights are
small (a 256→1536 and a 2048→1536 MLP). Pass `temb [1, 1536]` in as an ordinary input
with its own tight encoding. This is exactly trap #20's argument for hoisting RoPE, and
it deletes the `Sin`/`Cos`/`Concat`/`Gemm`/`Sigmoid`/`Mul` subgraph as a bonus.

> Do **not** try to hoist the per-block modulation itself. It is
> `block.norm1.linear(silu(temb))` with per-block weights — 18 blocks × 2 streams ×
> 1536 × 9216 ≈ 509 M params ≈ 2 GB fp32 on the host. The chunk split is the cheap fix.

## What was measured this session

### The per-block picture (the reason we now look at block 0)

Image stream, device vs onnxruntime fp32, case 0 (whose end-to-end SNR is 14.51 dB):

```
block 0 -> 23.49 dB      block  6 -> 21.94      block 12 -> 18.55
block 1 -> 24.39         block  7 -> 22.05      block 13 -> 16.49
block 2 -> 23.99         block  8 -> 21.54      block 14 -> 12.64
block 3 -> 21.73         block  9 -> 20.74      block 15 -> 11.30
block 4 -> 22.95         block 10 -> 19.69      block 16 -> 11.32
block 5 -> 22.41         block 11 -> 17.71      block 17 -> 27.63*
                                                noise_pred -> 14.51
```

`*` block 17's jump is a magnitude artefact — `max|ref|` rises 7.3e3 → 1.78e4.

**No smooth accumulation.** The stream loses everything it is going to lose in block 0
and then sits at 21–24 dB for six more blocks. **Trap #3's residual-accumulation story
is dead twice over** — once by host replay (53.33 dB, session 4) and now by the device's
own intermediates. Do not fold residual scaling into the weights hoping it will help.

The **text stream collapses at block 2** — 16.88 → **2.93 dB** — then *rises*
monotonically to ~14 dB. Rising SNR is not repair: the text residual grows 197 → 27,922,
so a fixed absolute error shrinks in relative terms. Worth a look after the AdaLN fix,
since `norm1_context`'s chunks are the worst of all (11.97 dB) and feed exactly that
stream.

### Hypothesis 7, dead: clipping

Checked first because it is the one thing the host ablations structurally *cannot* see —
`quant_ablate.py` derives each range from the tensor it is quantising, so it can never
saturate. `work/device/clip_scan.py` compares every activation's true fp32 range against
the interval `net.json` calibrated:

```
tensors whose real range LEAVES the calibrated encoding: 443 of 2123
total clipped elements across 3 cases:                   184,944
worst overflow:                                          0.299 x span
```

Worst offenders are all in blocks 9–17, a handful of elements each. **Nothing in
block 0.** Saturation is real and second-order; it cannot explain a block-0 loss.

**Seven hypotheses are now dead: padding, outlier ranges, 8-bit K/V, the −100 mask,
residual accumulation, W8 weights, clipping.** Do not re-run any of them.

### The control that makes the dump trustworthy

`--debug` and `--set_output_tensors` only work against `--model`, never a context
binary. So the whole exercise is worthless unless an online-prepared graph computes what
the shipping artefact computes. It does, case for case:

| build | deploy SNR, 16 held-out cases |
|---|---|
| context binary `mmdit_s0_v79.bin` (`--retrieve_context`) | 19.48 dB |
| **aarch64 model lib, online prep, same htp config** | **19.48 dB** (min 12.16) |

The htp config (`vtcm_mb 8`, `O 3.0`, `v79`, `soc_model 69`, burst) is passed explicitly
on the online path so the comparison isolates quantisation from graph-prep defaults.
And the fp32 reference is sound: onnxruntime on the same ONNX that was converted, fed
the same input raws, reproduces the stored `nref` at **121.73 dB**.

**Online prep of a 1.5 GB graph took 65 seconds**, not the minutes the last handoff
feared. Prefer the model lib over the context binary for all future diagnostics.

## New traps

> **28b. `--debug` does not scale.** Forcing all 2374 intermediates client-readable makes
> HTP finalize fail outright — `Finalize Graph for Idx = 0 failed with error = 1002`,
> after 1:55 of trying. 314 tensors finalize in 86 s; 35 in 71 s. Take the dump a slice
> at a time with `--set_output_tensors`; `block_tensors.py` picks the slice.

> **29. The converter's tensor names are the ONNX names with every non-identifier
> character replaced by `_`.** `/norm1/norm.12/Constant_1_output_0` →
> `_norm1_norm_12_Constant_1_output_0`. That makes a device dump joinable to an ONNX
> reference **mechanically, for every tensor** — which is what `layer_snr.py` exploits,
> and it is why onnxruntime is a far better reference here than torch: proto load 0.002 s
> (`load_external_data=False`), session build 11 s, **inference 1.5 s**, against loading
> a 1.5 B-parameter torch model. Append the wanted intermediates to `graph.output` and
> re-save **into the same directory** so the external-data path still resolves.

> **30. `qnn-model-lib-generator` builds in a temp dir under the CURRENT WORKING
> DIRECTORY**, and it explodes the weight blob into ~900 `.raw` files, `llvm-objcopy`s
> each into a `.o`, then links. Run it with cwd on `/mnt/c` and every one of those
> crosses the 9p mount; peak scratch was **4.2 GB on C:**. `cd` to ext4 first.

> **31. A tensor that feeds a `chunk`/`split` gets ONE encoding sized by its largest
> part.** Every smaller part then pays the full magnitude ratio in effective bits. In the
> MMDiT the six AdaLN modulation chunks span 1.68 → 18.41, so the small ones land at
> 12–14 dB while the tensor as a whole reads 29 dB. **Look for this wherever a single
> Linear produces several semantically different outputs** — it is invisible in the
> tensor's own encoding quality and only shows up in the slices.

> **32. Conv outputs read as garbage in a name-matched layerwise diff, and it is an
> artefact.** `_proj_Conv_output_0` scores **−2.99 dB** against ONNX while the very next
> `Reshape` scores 57 dB: the device writes the conv output channel-last while ONNX is
> channel-first, so the two tensors are a permutation apart. Ignore raw conv outputs in
> `layer_snr.py`; read the first layout-neutral tensor after them.
