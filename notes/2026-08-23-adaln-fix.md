# Session 6 — the AdaLN fix, built and measured (2026-08-23)

Session 5 located the Phase 5 accuracy gap in the AdaLN modulation path and named two
causes. This session **weighed them, built both fixes, and measured the result.**

> **Read `docs/phase5-mmdit-accuracy.md` for the standing answer.** This file is the
> session's working record: what was changed, what it cost, and what it bought.

---

## 1. The two causes are not equal — one of them is ~0.3% of the effect

Before spending a 35-minute conversion, the two candidate causes were weighed against
each other using **data already on disk** (`work/device/dnam_s0_snr.txt`, the session-5
device dump). The method is one line: turn each tensor's SNR back into an **absolute**
error, `err = rms(device) × 10^(−SNR/20)`, and compare it against the quantisation step
the shared encoding actually imposes.

| tensor | SNR dB | rms | **err rms** |
|---|---:|---:|---:|
| `_norm1_linear_Gemm_output_0` | 29.35 | 1.157 | **0.0394** |
| `_norm1_Slice_0` (shift_msa) | 16.93 | 0.255 | **0.0363** |
| `_norm1_Slice_1` (scale_msa) | 28.24 | 1.082 | **0.0419** |
| `_norm1_Slice_2` (gate_msa) | 20.44 | 0.358 | **0.0341** |
| `_norm1_Slice_3` (shift_mlp) | 13.90 | 0.161 | **0.0325** |
| `_norm1_Slice_4` (scale_mlp) | 26.94 | 1.004 | **0.0452** |
| `_norm1_Slice_5` (gate_mlp) | 34.85 | 2.373 | **0.0429** |
| `_norm1_context_Slice_{0..5}` | 11.97 – 27.50 | 0.150 – 1.070 | **0.0378 – 0.0465** |

The signal rms spans **16×** and the SNR spans **23 dB**, while the absolute error is
flat at **0.032 – 0.046** across all fourteen tensors. That is a constant additive error
arriving from upstream, not an encoding fault in the chunks.

And the encoding fault can be sized exactly. `net.json` gives the parent Gemm
`scale = 4.69191e-4`, shared by all six slices — trap #31 is genuinely present — so the
noise the sharing imposes is `4.69191e-4 / √12 = 1.354e-4`: **291× to 343× smaller than
the error that is actually there.**

**Cause 1 (the shared chunk encoding) is real and harmless. Cause 2 (the conditioning
path) is the whole thing.** The dump traces it end to end:

| tensor | SNR dB |
|---|---:|
| `time_proj_Sin` / `Cos` — quantised at an argument encoded over `[0, 1000]` | 46.41 / 47.32 |
| `timestep_embedder_linear_1_Gemm` | 39.92 |
| `timestep_embedder_act_Mul` (the SiLU) | **28.50** |
| `timestep_embedder_linear_2_Gemm` | 45.94 |
| `time_text_embed_Add` (= `temb`) | 43.14 |
| `norm1_silu_Sigmoid` | 24.71 |
| `norm1_linear_Gemm` | 29.35 |

Both fixes were built anyway — the split is free — but the expectation going in was that
**the hoist carries the result and the split contributes almost nothing.**

## 2. What changed in the export

`work/export/export_mmdit_stage.py`, both changes verified bit-exact against the stock
model before anything was converted.

**(a) `time_text_embed` and its SiLU hoisted to the host.** New `host_temb()` returns
`silu(time_text_embed(timestep_ratio, pooled_projections))` as `temb_act [1, 1536]`, and
the graph takes it as an ordinary input. Every consumer inside the graph — `norm1`,
`norm1_context`, `norm_out`, 37 of them — begins with `self.linear(self.silu(emb))`, so
the SiLU is the same tensor for all of them and hoisting it too is free. This deletes
`Sin`/`Cos`/`Concat`/two `Gemm`s/`Sigmoid`/`Mul` **and 37 SiLUs**, and replaces a 46 dB
tensor with an input that carries its own tight 16-bit encoding.

The graph inputs change: `pooled_projections` and `timestep_ratio` are gone, `temb_act`
takes their place. `--input_layout temb_act NONTRIVIAL` (trap #23 — no image semantics).

**(b) Each AdaLN modulation Linear split into its chunks.** New `SplitMod` slices
`norm1.linear` (1536→9216) into six 1536→1536 Linears, `norm1_context.linear` likewise
(two for the `context_pre_only` block, which is `AdaLayerNormContinuous`), and
`norm_out.linear` into two. Weight rows are taken as **views** — `nn.Parameter(W[a:b])`
shares storage — so 509 M params of modulation weight are not duplicated on the host.

The `+1` of `(1 + scale)` is folded into each scale Linear's bias, which is exact
(`(W·a + b) + 1 == W·a + (b + 1)`) and removes one op and one 16-bit encoding per chunk.
Note the chunk order flips between the two AdaLN classes — `AdaLayerNormZero` is
`(shift, scale, gate) × 2` so the fold lands on indices 1 and 4, while
`AdaLayerNormContinuous` is `(scale, shift)` so it lands on index 0.

Both are togglable for ablation: `--no-split-mod`, `--in-graph-temb`.

### fp32 equivalence, before any conversion

```
[check] PASS -- worst max|diff| over 18 shape(s): 1.144e-05     (123.7 - 127.6 dB)
[pad]   PASS -- the envelope graph reproduces every short unit  (123.3 - 127.4 dB)
```

Every one of the 18 (unit, stage) shapes and every short unit through its stage's
padding envelope, at the fp32 floor. The rewrite is exact.

### The graph got *smaller*

| | baseline `mmdit_s0` | fix `mmdit_s0f` |
|---|---:|---:|
| nodes | 2378 | **2192** |
| FullyConnected | 255 | 428 |
| StridedSlice | 324 | **108** |
| Transpose | 121 | 121 |
| **transpose / compute ratio** | **0.18** | **0.18** |

173 more `FullyConnected` (the split) but 216 fewer `StridedSlice` (the `chunk(6)`) and
the whole `time_text_embed` subgraph gone: **186 fewer ops overall.** The layout
structure is untouched — same 121 Transposes, same ratio, and the byte counts differ by
exactly 2× because the layout build is fp32 and the shipping build is A16 (trap #24).

## 3. Infrastructure: variants can now coexist

Every stage-0 script was keyed on `mmdit_s${STAGE}`, which made an A/B impossible
without destroying the baseline. They now take a `NAME`:

| script | how |
|---|---|
| `work/qnn/convert_mmdit_w8a16.sh` | `NAME=mmdit_s0f ./convert_mmdit_w8a16.sh 0` — selects the ONNX dir, the calib dir and every output |
| `work/qnn/build_android_lib.sh` | same `NAME`; now also `cd`s to ext4 first (trap #30) |
| `work/device/run_mmdit.sh`, `run_mmdit_lib.sh` | `NAME=…`; output dirs key on `SUF=${NAME#mmdit_}`, so `NAME=mmdit_s0` reproduces every old path exactly |
| `work/device/push_mmdit.ps1`, `push_mmdit_lib.ps1` | `-Name mmdit_s0f` |
| `work/device/make_mmdit_io.py` | `--out-name`, plus `--cond temb\|raw` for the hoist ablation |
| `work/device/compare_mmdit.py`, `layer_snr.py` | `--name` |
| `work/qnn/run_s0f.sh` | new: the WSL entry point, because `wsl -e bash -lc "NAME=… …"` does not survive the quoting |

> **New trap. `wsl -d Ubuntu -e bash <script>` inherits the Windows environment, and
> Windows already defines `NAME`** (it holds the machine/user name). A
> `NAME=${NAME:-mmdit_s0f}` default-if-unset therefore silently tried to convert a graph
> called `<HOSTNAME>`. Assign the variable unconditionally in any script launched
> through WSL interop, or pass it as a positional argument.

## 4. Result: 19.48 -> 27.89 dB

Same 16 held-out cases, byte-identical inputs, same `nref` references (the two reference
sets agree at 130.2 dB), so this is directly comparable to the session-5 number.

| | session 5 `mmdit_s0` | **session 6 `mmdit_s0f`** | target |
|---|---:|---:|---:|
| deploy SNR, mean of 16 | 19.48 dB | **27.89 dB** | 29.0 dB |
| deploy SNR, min | 12.16 dB | **24.47 dB** | — |
| nan / inf | 0 | 0 | — |

**+8.41 dB on the mean, +12.31 dB on the worst case.** 1.11 dB short of the paper's
stage-0 target.

The encodings show the split landed exactly as designed. Where the six chunks used to
share one 16-bit encoding of `scale = 4.69191e-4`, they now carry six:

| chunk | scale | calibrated range |
|---|---:|---|
| `_mod1_0_parts_0` (shift_msa) | 5.062e-5 | [-1.239, 2.078] |
| `_mod1_0_parts_1` (1+scale_msa) | 1.932e-4 | [-6.580, 6.080] |
| `_mod1_0_parts_2` (gate_msa) | 9.703e-5 | [-3.112, 3.247] |
| `_mod1_0_parts_3` (shift_mlp) | 4.150e-5 | [-1.035, 1.684] |
| `_mod1_0_parts_4` (1+scale_mlp) | 1.025e-4 | [-3.336, 3.380] |
| `_mod1_0_parts_5` (gate_mlp) | 4.640e-4 | [-11.78, 18.63] |

The smallest chunk's step is **11x finer** than it was. And `temb_act` arrives as an
input encoded over `[-0.266, 15.22]` — step 2.36e-4, a ~94 dB ceiling — in place of an
in-graph tensor that measured 24.71 dB.

Graph health is unchanged: zero float fallback, 2221 `UFIXED_16` / 626 `UFIXED_08`
tensors, and `matmul_bits.py` reports the same `54x MatMul u16 x u8` as the baseline
(the known dead-end; `DYN16=1` still opts in).

### The control is bit-exact this time

Session 5 could only show that the online-prepared model lib *matched the context binary
in aggregate SNR*. On this build the two produce **the same bytes**:

```
context binary   vs fp32  : 24.47 dB      (case 0)
aarch64 model lib vs fp32 : 24.47 dB
lib vs context binary     : max|d| = 0.000e+00
```

So every intermediate the model lib dumps is exactly what the shipping artefact computes.

### Latency: free — in fact 1.3% faster

The first attempt measured the fix alone, three rounds of six: **291.8 / 265.4 /
192.9 ms**, monotonically falling. That is not a latency measurement, it is a picture of
the DSP clock ramping, and it is exactly the trap #10 failure mode — none of those
numbers is comparable to the baseline's recorded 172.2 ms.

`work/device/ab_mmdit.sh` alternates the two context binaries A B A B A B in one
session, each with its own input directory (the two graphs take different inputs), and
scores each by min-of-N across its rounds:

| build | r1 | r2 | r3 | **min** |
|---|---:|---:|---:|---:|
| `mmdit_s0` (session-5 baseline) | 171.5 | 171.8 | 171.7 | **171.5 ms** |
| `mmdit_s0f` (session-6 fix) | 173.4 | 169.2 | 169.9 | **169.2 ms** |

Interleaving collapses the 99 ms spread to a 169-173 ms band and reproduces the
baseline's known 172.2 ms. **+8.41 dB of accuracy for -1.3% of latency** — which the op
census predicted: the graph is 186 ops smaller, the 214 `StridedSlice [1,1536]` that
`docs/phase5-mmdit-latency.md` measured at 5.0% are gone, and the 173 extra
`FullyConnected` are the same total MACs redistributed.

## 5. Where the remaining 1.11 dB is *not*

### Padding does not set the encodings (measured, new)

The per-case pattern is striking — SNR tracks how much padding the case carries:

| case | unit | padded tokens | SNR |
|---:|---:|---:|---:|
| 0 | 1 | 200 | 24.47 |
| 1 | 2 | 160 | 27.48 |
| 5 | 6 | 0 | 28.50 |
| 6 | 1 | 200 | 25.98 |
| 11 | 6 | 0 | 29.84 |

The obvious mechanism: padded rows flow through every tensor and take part in the
min/max that calibration derives, so if they are *larger* than real rows, real tokens pay
for their range in effective bits. `work/device/pad_ranges.py` measures it directly —
max|x| over padded image rows vs real ones, at all 37 residual boundaries of case 0
(71% padded):

```
block  0 in   pad 1.492    real 9.326      0.16x
block  9 in   pad 1250.6   real 2423.2     0.52x
block 17 mid  pad 11925.3  real 13580.0    0.88x
norm_out      pad 16599.7  real 17807.7    0.93x
worst pad/real ratio: 0.93x
```

**Padded rows are smaller than real ones everywhere — never once above 1.0x.** They
cannot be setting any encoding. Padding stays dead as a mechanism; the unit-1 penalty is
real but comes from something else.

### A faithful W8A16 simulation still says 43 dB

`quant_ablate.py`, re-pointed at the new graph (the split Linears alias
`norm1.linear.weight` as views, so quantising the parent covers them):

| group | deploy SNR, case 0 |
|---|---:|
| nothing quantised | inf |
| W8 per-channel weights, 249 Linear / 1498 M params | **43.14 dB** |
| A16 on every Linear output | 79.15 dB |
| A16 softmax over [0,1] | 96.38 dB |
| **the device** | **24.47 dB** (case 0) |

Identical to the session-4 numbers, which is itself the point: the host simulation never
modelled the conditioning path, so fixing it moved the device 8.4 dB while leaving the
simulation exactly where it was. The device is now **18.7 dB** from a faithful W8A16
execution of its own graph rather than 23.7 dB — the same unexplained residue, smaller.

The block-boundary dump for the new build is captured
(`work/device/dblk_s0f`, 35 tensors, bit-exact control) and is the next thing to read.

## 6. Stage 1: a second, unrelated bug — the concat is executed round-robin

With stage 0 at 27.89 dB, stage 1 was exported, calibrated (300 real samples), converted
and measured the same way. It came back at **−0.13 dB** — not degraded, *broken*.

### What it is not

Every cheap explanation was eliminated before any expensive one was attempted:

| ruled out | how |
|---|---|
| index misalignment between outputs and references | every device output correlates best with its OWN reference (0.20–0.40), none with another's |
| a token permutation | sorted-value SNR is 15.6 dB, not ∞ |
| a rank-3 layout misread (trap #23/#32) | all six rank-3 reinterpretations score ≤ −1.49 dB (`layout_probe.py`) |
| a wrong ONNX | `noise_pred` scores −0.93 dB against **both** onnxruntime and the stored torch reference, which therefore agree with each other |
| an inherently unquantisable graph | host W8 simulation of the same graph: **36.73 dB** |
| graph-prep options (`vtcm_mb 8`, `O 3.0`) | `accdef`, with no config file at all, gives the identical −0.13 dB |
| structure or encodings | `net.json` is node-for-node identical to stage 0 (2246 nodes, zero float fallback), and every encoding along the patchify and attention paths is healthy |

### What it is

The block dump splits the two streams cleanly:

| stream | block 1 | block 5 | block 13 | block 17 |
|---|---:|---:|---:|---:|
| **image** (520 tok) | **−1.49 dB** | −1.42 | −0.46 | 2.52 |
| text (128 tok) | 17.43 | 15.22 | 11.25 | 10.58 |

and the block-0 interior finds the exact edge:

| tensor | shape | SNR |
|---|---|---:|
| `_Concat_output_0` — patchified image tokens | `[1,520,1536]` | **52.82 dB** |
| `_norm_LayerNormalization_output_0` — **image** | `[1,520,1536]` | **2.73 dB** |
| `_norm_1_LayerNormalization_output_0` — **text** | `[1,128,1536]` | **72.37 dB** |

A 52.8 dB tensor enters a LayerNorm and leaves at 2.73 dB, while the *same node type*
with identical parameters computes the text tensor at 72.4 dB.

`rowscan.py` then shows the damage is uniform across all 520 rows (0.9–6.2 dB) with the
right magnitude range, and every device row has mean 0 and std 1 — a perfectly valid
LayerNorm **of the wrong row**. Matching each device row to its reference row by cosine
gives **1.0000 for every row**: an exact permutation. Its run structure is

```
dev   0:25  <- ref   0:25       8 rounds of
dev  25:45  <- ref 200:220        25 rows from slot 0  (200/8)
dev  45:65  <- ref 360:380        20 rows from slot 1  (160/8)
dev  65:90  <- ref  25:50         20 rows from slot 2  (160/8)
...
```

**QNN split each of the three concat inputs into eight equal chunks and round-robined
them.** Applying that permutation to the fp32 reference scores **81.85 dB** — the
arithmetic was never wrong, only the order.

### Why that is fatal here, and only here

`attn_mask`, `rope_cos` and `rope_sin` are **host-supplied and indexed by sequential
token position** — that is trap #20, the thing that makes front-padding exact. Interleave
the tokens and every one of them gets the wrong position id and the wrong mask row, so
block 0's attention destroys the image stream. Re-applying the permutation does *not*
rescue block 1 (5.08 dB), confirming the information is destroyed, not merely reordered.

Three details explain why nothing else showed it:

- the **text stream never passes through that concat** — 72 dB while the image stream is 2.7 dB
- **stage 0's 280-token concat is not chunked at all**: its rows map identity, mean cosine 1.0000
- it is **invisible in every static artefact** — both graphs declare `axis: 1` and an
  identity `permute_order_to_src`, and both have the same 2246 nodes

### First attempt: move the concat to the outermost axis — did NOT work

Trap #26 already measured that a concat on the **outermost** axis is folded into its
producers' allocation and costs exactly zero cycles — a different code path from the one
doing this chunking. So both token streams now travel at **rank 2, `[S, C]`**, and the
patchify concat is `torch.cat(..., dim=0)`.

The rewrite is mechanical (every `[1, S, C]` becomes `[S, C]`, and each `[1, C]`
modulation vector broadcasts without the inserted token axis) and it is **exact**:
stage 1 verifies at 126.0 dB against the stock model, unchanged. Graph inputs and the
output keep their shapes — the text stream is reshaped inside `forward` — so the
calibration and test sets did not have to be rebuilt.

It also makes the graph leaner: `MatMul` 268 → **54** (rank-2 Linears lower to `Gemm`,
428 of them), `Add` 573 → **359**, `Constant` 1304 → **1091**; converted, the node count
falls **2246 → 1715** (`Reshape` 669 → 138) and the transpose ratio **0.18 → 0.14**.

**But it did not fix the interleave.** The converted graph shows `_Concat` with
`axis: 0` on three rank-2 inputs, and the device reproduces the *identical* permutation —
45 of 520 rows in place, same 25/20/20 runs. Moving the concat outermost made it *more*
foldable, not less.

The re-read of the evidence explains why: the dumped `_Concat_output_0` is correct in
identity order (52.82 dB) while its consumer's output is permuted, and
`concat(dumped parts)` matches the dumped concat at 79.23 dB. **The concat is virtual.**
Its consumer reads the three producer buffers directly — exactly what trap #26 says an
outermost-axis concat does — and it is the consumer's partitioning that interleaves them.

### The reproducer, and what it pins down

Iterating inside the real model costs ~55 minutes per attempt, so
`work/audit/concat_repro.py` builds three-node graphs — N inputs → join → LayerNorm →
output — with the same shapes. `work/device/run_repro.ps1` converts, pushes, runs and
scores one in **about two minutes**. The tiny graph reproduces the fault exactly: same
25/20/20 × 8 interleave, 45 of 520 rows in place.

| variant | shape | rows | result |
|---|---|---:|---|
| `s0` | [200,40,40] rank 2 | 280 | **order preserved** (83.52 dB) |
| `two300` | [200,100] rank 2 | 300 | order preserved |
| `two320` | [200,120] rank 2 | 320 | order preserved |
| `two360` | [200,160] rank 2 | 360 | **INTERLEAVED** |
| `cat3` | [200,160,160] rank 2 | 520 | **INTERLEAVED** |
| `cat3r3` | same, rank 3 axis 1 | 520 | **INTERLEAVED** |
| `cat2` | nested two-input concats | 520 | **INTERLEAVED** (QNN flattens them back) |
| `qk0` | [128,280] rank 3 `[n,24,64]` | 408 | **order preserved** (83.69 dB) |
| `qk1` | [128,520] rank 3 `[n,24,64]` | 648 | **order preserved** (83.88 dB) |
| `padadd` | [200,160,160], no concat | 520 | **ORDER PRESERVED** (81.82 dB) |

Three things fall out:

1. **The threshold is between 320 and 360 rows** for a rank-2 `[N, 1536]` concat. Stage 0
   sits at 280 and is safe by 40 rows — it was never a correct graph, only a lucky one.
2. **Rank-3 `[n, 24, 64]` is immune even at 648 rows.** That is why the *attention*
   concat — `cat([eq, q], dim=0)` on `[n, 24, 64]`, which RoPE and the mask are applied
   after and which would be just as fatal — is fine in both stages. Only patchify is hit.
3. **Neither nesting nor rank changes anything.** The only thing that works is not having
   a concat.

### The fix: `_join()` — zero-pad each group and sum

`patchify` no longer calls `torch.cat`. Each token group is padded with zeros to the full
length and the groups are summed; they are disjoint, so the sum *is* the concatenation,
exactly. Verified at 126.0 dB against the stock model, unchanged.

The cost is two extra elementwise adds over the full token tensor, once, at patchify.

> **New trap. A rank-2 multi-input concat above ~320 rows is executed as EIGHT
> round-robin chunks, and nothing in `net.json` says so.** QNN reads the three producer
> buffers of stage 1's `[200,1536] + [160,1536] + [160,1536]` concat in the order
> 25,20,20, 25,20,20, … The arithmetic stays perfect — applying the permutation scores
> 81.85 dB — so it only surfaces where something *outside* the tensor is indexed by
> position, here the host-hoisted RoPE and mask (trap #20). Measured thresholds:
> 320 rows fine, 360 rows broken; rank-3 `[n,24,64]` immune at 648. Moving the axis,
> nesting the concats and changing rank all fail; **padding each group to full length
> and summing is what works.** `work/audit/concat_repro.py` + `run_repro.ps1` test a
> variant in two minutes — use them before believing any concat is safe.

> **Corollary: stage 0 was lucky, not correct.** Its patchify concat is 280 rows, 40
> below the threshold. Any future stage, envelope or padding change that pushes a rank-2
> concat past ~320 rows would have silently broken it the same way.

> **Tooling trap. Do not write a `--set_output_tensors` list with PowerShell `>`.**
> It emits a UTF-8 BOM and CRLF, so the first name in the list carries a BOM and the last
> carries a `\r`; `qnn-net-run` silently skips both and dumps N−2 tensors. That cost the
> single most useful tensor in the first stage-1 dump — block 0's image output. Write it
> from Bash, or with an explicit ASCII/no-newline writer.

### Result: -0.13 dB -> 23.99 dB, target MET

Same 16 held-out cases, same references.

| | before `_join` | **after** | target |
|---|---:|---:|---:|
| deploy SNR, mean of 16 | -0.13 dB | **23.99 dB** | 22.0 |
| deploy SNR, min | -0.93 dB | **21.98 dB** | — |
| latency, min-of-3 | — | **375.8 ms** | 218.3 |

A **24 dB** swing from replacing one `torch.cat` with a pad-and-sum. Stage 1 is the first
MMDiT stage to clear its paper target.

Latency is 1.72x the paper's number, in line with stage 0's 1.62x.

## 7. All three stages on device

Stage 2 converted with the same `_join` fix (its four slots are 160/160/640/640 rows,
every join past the 320-row threshold) and came back **working, not broken** — which is
itself the confirmation that `_join` did its job there too.

| stage | tokens | accuracy | target | verdict | latency min | paper |
|---|---:|---:|---:|---|---:|---:|
| 0 | 408 | 27.89 dB | 29.0 | -1.11 | 169.2 ms | 104.7 |
| 1 | 648 | **23.99 dB** | 22.0 | **MET** | 375.8 ms | 218.3 |
| 2 | 1728 | 20.01 dB | 24.0 | -3.99 | 1851 ms | 938.3 |

Converter wall times: 38:32 / 48:43 / **2:52:07**. The last one is superlinear in
sequence length — a single `[24,1728,1728]` score matrix is 143 MB in fp32, so the
quantiser's min/max pass over 300 calibration samples becomes memory-bandwidth bound
rather than FLOP bound. Budget ~3 h for any stage-2-sized conversion.

Graph health improves with the rewrite, monotonically with stage size:

| | stage 0 (old path) | stage 1 | stage 2 |
|---|---:|---:|---:|
| nodes | 2246 | 1715 | 1730 |
| transpose / compute | 0.18 | 0.14 | **0.06** |
| `Concat` | 58 | 57 | **54** |
| float fallback | 0 | 0 | 0 |

54 is exactly 18 blocks x 3 (q, k, v) — the patchify concat is gone entirely, and every
concat that remains is the rank-3 attention join the reproducer proved safe.

### Two patterns worth carrying forward

**Accuracy falls with sequence length: 27.89 / 23.99 / 20.01 dB at 408 / 648 / 1728
tokens.** That is the residual-accumulation signature the stage-0 layerwise dump already
showed (33.10 dB after block 0 decaying to 21.63 by block 16) — more tokens per residual
add, more accumulated error. Stage 2 has both the longest sequence AND the highest target
(24 dB vs stage 1's 22), which is why it is the worst gap.

**Latency is a consistent 1.6-2.0x the paper**: 1.62x / 1.72x / 1.97x. Over the AR loop
that is 6 x (169.2 + 375.8 + 1851) = **14.4 s** of MMDiT per 49-frame video against the
paper's 7.6 s.

> **Tooling trap, second sighting. PowerShell writes CRLF, and QNN's list files are
> parsed byte-exactly.** `Set-Content` on a rewritten `calib_list_host.txt` put `\r` at
> the end of every line, so the last path on each line did not exist and the converter
> aborted with "300 calibration files missing". This is the same fault that silently
> dropped two tensors from a `--set_output_tensors` list earlier in the session. **Any
> list file consumed by the QNN toolchain must be written LF-only and BOM-free** — write
> it from Bash, or with an explicit ASCII/no-newline writer.

## 8. Phase 3 and the first-frame path

With the video path complete, the session moved to the modules the AR loop needs seeded:
the SSD1B first-frame pipeline plus the ContextAdapter.

### The ContextAdapter -- the second module the plan never listed

`generation_utils.py:501` runs `prompt_embeds = context_adapter(prompt_embeds)`,
[1,128,4096] -> [1,128,1536], and 1536 is exactly the MMDiT's `encoder_hidden_states`
width. It appears in no phase of the plan and in no row of Table 9 -- the same shape of
omission as Phase 4b (the VAE encoder).

It took six builds, and the last one is the one that mattered:

| build | SNR |
|---|---:|
| W8A16, per-tensor weights | 2.62 dB |
| + `--use_per_row_quantization` | 4.61 |
| + W16 weights | 5.13 |
| + clamped GELU (bit-exact) | 6.80 |
| W16 + clamp + per-row | 9.44 |
| **FP16, no quantisation** | **39.36** |

See traps #33/#34/#35 in `docs/trap-audit.md`. The short version: a host simulation said
per-row W8 could not exceed 16.84 dB on this module *before any of those builds*, and
Table 9 deploys the whole text path in FP16 anyway.

### SSD1B UNet (Phase 3) -- 32.51 dB against a 33 dB target, first try

1331.3 M params, 640x1024 -> latent 80x128, 4 steps, `guidance_scale 0.0` so batch 1.
Two lessons were applied BEFORE the first conversion instead of after:

* **Both sinusoidal embeddings hoisted to the host.** diffusers 0.35.1 routes them through
  overridable `get_time_embed()` / `get_aug_embed()`, so the graph takes `t_emb [1,320]`
  and `aug_emb [1,1280]` as ordinary inputs and no copy of the 150-line forward is needed.
  Bit-exact against stock (max|diff| 0.000e+00). This is the trap that cost the MMDiT
  8.41 dB.
* **`--use_per_row_quantization` from the start** -- 427 signed-8-bit per-row weight
  tensors in the converted graph, versus 0 in every earlier build.

Screened before spending device time: transpose/compute **0.15** (livable), GroupNorm
**43/43 fused** (trap #17 again), zero float fallback.

| | |
|---|---|
| conversion | **3:29** -- the longest in the project, past MMDiT stage 2's 2:52 |
| context binary | 1.358 GB |
| **deploy SNR** | **32.51 dB mean, 23.91 min** (Table 9: 33) |

The per-case numbers have a clean structure -- SNR tracks the denoising step:

| step | timestep | SNR |
|---|---|---|
| 1 | 999 | 42.98 / 42.62 / 40.94 / 43.52 |
| 2 | 749 | 32.16 / 35.24 / 31.49 / 34.70 |
| 3 | 499 | 26.59 / 28.73 / 27.20 / 29.01 |
| 4 | 249 | 26.99 / 25.88 / 23.91 / 28.15 |

Accuracy falls monotonically as denoising proceeds: the early high-noise steps are easy,
the late low-noise steps are where the signal is small against a fixed quantisation error.
The mean is dragged down entirely by steps 3-4 -- and step 4 is the one that determines
the frame you actually see.

**Remaining transpose traffic is the attention head reshuffle**, `[1,heads,tokens,64]` <->
`[1,tokens,heads,64]` (diffusers' `head_to_batch_dim`), 889 MB and 19%+19%+12%+12% of the
total. The MMDiT fixed the same thing by going rank-3 with tokens on axis 0 (1.35 ->
0.25). Not chased here: 889 MB x 0.252 ms/MB x 4 steps is ~0.9 s per video against a
~14.4 s MMDiT budget, and it would mean patching diffusers' attention processor.

### CLIP L -- 60.75 dB

FP16, no calibration, exactly as Table 9 specifies. Correlation 1.0000, zero non-finite,
234 MB, ~2 minutes to convert. The best number in the pipeline. Peak activations are 833
(CLIP L) and 145 (CLIP G) against fp16's 65504, so trap #3's NaN risk -- which forced
residual scaling on DistilT5 -- does not apply.

### Two capture bugs, same root cause

Both the UNet and the VAE-decoder captures initially recorded **nothing**, for related
reasons, and both were caught by smoke-testing on 2-4 prompts before committing GPU hours:

* **UNet:** `unet.forward = spy` survived only the first generation.
  `enable_model_cpu_offload()` installs accelerate hooks that re-bind `module.forward`, so
  an instance-attribute patch is silently undone. Symptom: prompt 1 captured 4 calls,
  prompt 2 captured 0. A `register_forward_pre_hook` is re-entrant and survives.
  (`capture_mmdit_calib.py` got away with the monkeypatch because its DiT was not offloaded.)
* **VAE decoder:** a pre-hook on `vae` never fires, because the pipeline calls
  `vae.decode(z)` and never `vae.__call__`. 32 prompts, 0 captures. The right point is
  `vae.post_quant_conv` -- which `run_reference.py` line 15 already documented.

> **Rule: smoke-test a capture on 2-4 prompts and assert it captured what you expect
> before spending GPU hours.** Both bugs cost minutes because of that; either would have
> cost an hour otherwise.

## 9. END TO END ON THE PHONE

Both halves of the pipeline now run on the NPU.

### First frame: prompt -> image, entirely on device

`work/pipeline/run_npu_firstframe.py`: CLIP L + CLIP G -> SSD1B UNet x4 -> SSD1B VAE
decoder, six graph invocations, producing a 1024x640 PNG. The latent trajectory is a
textbook LCM schedule (rms 0.983 -> 0.947 -> 0.888 -> 0.847) and the image has per-channel
std ~72, so it is a real image rather than a collapsed one.

Everything not a converted module stays on the host and comes from the reference: the
tokenisers, the LCM scheduler's step maths, and the two sinusoidal projections that were
deliberately hoisted out of the UNet graph.

> The scheduler must be constructed EXACTLY as the reference does --
> `LCMScheduler(set_alpha_to_one=False, original_inference_steps=4, steps_offset=1)`.
> A default `LCMScheduler()` denoises on a different sigma schedule and would have
> produced a plausible-looking but wrong image, with nothing to indicate why.

### Video: 18 MMDiT calls on device

`work/pipeline/run_npu_video.py` substitutes `NpuPyramidMMDiT` and `NpuContextAdapter`
into `generate_hybrid()` and leaves the AR loop, the pyramid scheduler, the history
pyramid and the per-stage sigmas untouched. 6 units x 3 stages = **18 MMDiT calls**,
producing `(1, 16, 7, 40, 64)` latents = 49 frames.

### The compounding measurement -- the number the per-module SNRs could not give

Every stage SNR in this project was measured against **clean fp32 conditioning**. In the
real loop each unit conditions on the previous one, so the question was always whether
error compounds. Same seed, same prompt, NPU vs fp32 reference:

| latent frame | SNR | |
|---|---:|---|
| 0 | **inf** | host-generated first frame -- identical, which is what makes the rest trustworthy |
| 1 | **19.69 dB** | first AR unit, close to stage 2's standalone 20.01 |
| 2 | 12.36 | |
| 3 | 7.59 | |
| 4 | 7.54 | |
| 5 | 5.67 | |
| 6 | **4.41 dB** | last AR unit |
| **whole video** | **7.81 dB**, corr **0.9159** | |

**Error compounds at roughly -3 dB per AR unit.** Correlation 0.916 means the video is
still structurally similar rather than garbage, but ~60% relative error on the final frame
is likely visible drift.

Paper Table 9 reports per-module SNR only, so Qualcomm's deployment compounds the same way
and there is no published end-to-end figure to compare against.

> **Trap: `generate_hybrid()` takes no `generator`.** Both the first-frame noise and the
> video noise come from the GLOBAL torch RNG, so two runs are two different videos. The
> first comparison scored **0.11 dB** and looked catastrophic; the tell was that frame 0 --
> computed on the HOST in both runs and therefore necessarily identical -- read 2.68 dB.
> Seeding `torch.manual_seed()` before the call took the same comparison to 7.81 dB.
> **When an end-to-end number looks impossibly bad, check that the two runs are actually
> the same experiment before believing it.**

### What this changes

The highest-value accuracy work is now unambiguous: **MMDiT stage 2** (20.01 dB, 4 dB
below the paper) is the highest-resolution stage and runs last in every unit, so its error
is what compounds. And `--use_per_row_quantization` -- found today, trap #33 -- was never
applied to any MMDiT build, leaving all 428 fully-connected weights per-TENSOR 8-bit while
the host ablation that predicted 43.14 dB assumed per-channel weights it never got.
